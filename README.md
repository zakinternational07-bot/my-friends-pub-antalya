# My Friends Pub — Antalya

Сайт филиала паба в Анталии: фронтенд на чистом HTML/CSS/JS + backend на
Node.js/Express с SQLite, бронированием мест и оплатой в **тестовом режиме**.

## Быстрый старт

```bash
cd backend
npm install
cp .env.example .env
# открой .env и задай ADMIN_USERNAME / ADMIN_PASSWORD / SESSION_SECRET
npm run dev
```

Сервер поднимется на `http://localhost:3000` и отдаёт и API, и фронтенд.
Открой `http://localhost:3000/` — попадёшь на главную страницу.
Админка: `http://localhost:3000/html/admin/login.html`
(логин/пароль — те, что задал в `.env`).

При первом запуске автоматически создаётся `backend/data/mfp.sqlite` и
сидируются: админ-аккаунт, план зала (7 столов/зон), 3 примера мероприятий
на ближайшую неделю и пример меню на 3 языках — чтобы сайт не был пустым
"из коробки". Отредактируй/удали через админку.

## Что уже по-настоящему работает

- Бронирование мест с временным холдом (10 минут по умолчанию,
  `SEAT_HOLD_MINUTES` в `.env`) и защитой от двойного бронирования одного
  места на уровне транзакции БД.
- Живое обновление занятости мест между вкладками/устройствами через
  WebSocket (`/ws`), с поллингом раз в 15 сек как фолбэком.
- Генерация билета с QR-кодом и номером брони.
- **Подтверждение брони на бесплатные мероприятия через Telegram** —
  вместо оплаты (см. раздел ниже). Полностью настоящая интеграция,
  протестирована с реальным ботом и живым вебхуком.
- **Опрос по итогам визита** — через `SURVEY_HOURS_AFTER_EVENT` часов
  после начала мероприятия гостю с оплаченной/подтверждённой бронью
  уходит ссылка на мобильную веб-форму (4 оценки 1-5 + отзыв текстом).
  Ссылка отправляется в Telegram, если гость подтверждал бронь через
  бота, иначе на email. Ответы сразу пересылаются в чат персонала
  (`TELEGRAM_STAFF_CHAT_ID`) в формате `#Опрос`/`#отзыв`, а раз в неделю
  по понедельникам туда же уходит сводка средних баллов (см. раздел
  ниже).
- Админ-панель: мероприятия (заголовок, описание, дата/время, цена, одна
  зона загрузки фото ИЛИ видео — файл реально загружается и сразу
  показывается на сайте), меню на 3 языках (категории + пункты), план
  зала (JSON-редактор), просмотр всех броней.

## Что работает в тестовом режиме (без реальных денег/писем)

- **Оплата** — `backend/src/services/payment/MockPaymentProvider.js`.
  Подключение реального шлюза:
  1. Создать `backend/src/services/payment/IyzicoProvider.js` (или
     `PayTRProvider.js`), реализующий тот же интерфейс, что
     `PaymentProvider.js` (`createPayment`, `confirmPayment`).
  2. Добавить ветку в `backend/src/services/payment/index.js`.
  3. В `.env`: `PAYMENT_PROVIDER=iyzico` + API-ключи шлюза.
  4. Понадобится: юрлицо/ИП в Турции для приёма платежей, договор с
     эквайером, API-ключи из личного кабинета шлюза.
- **Письма с билетом** — `backend/src/services/email/ConsoleEmailService.js`
  логирует и сохраняет письмо в `backend/data/emails/*.html`, реально не
  отправляет. Подключение Resend/SendGrid — аналогично оплате, через
  `backend/src/services/email/index.js` и `EMAIL_PROVIDER` в `.env`.
  Понадобится: аккаунт в сервисе рассылки + API-ключ + подтверждённый
  домен отправителя.

## Telegram-подтверждение брони на бесплатные мероприятия

Для мероприятий с ценой 0 (`event.price === 0`) кнопка «Оплатить билеты»
на `booking.html` заменяется на «Подтвердить бронь в Telegram». Флоу:

1. Гость заполняет имя/email, выбирает места, жмёт кнопку — создаётся
   обычная held-бронь (10 минут на подтверждение, как и везде), но вместо
   `payment.html` гостя переносит в `t.me/<бот>?start=<токен>`.
2. Гость жмёт «Start» в Telegram → бот получает это через вебхук
   (`POST /api/telegram/webhook`), находит бронь по токену, помечает
   `status = 'paid'` (место занято) и шлёт гостю подтверждение с деталями
   брони.
3. Раз в 10 минут (`backend/src/services/reminderScheduler.js`) сервер
   проверяет неподтверждённые (`attendance_status = 'pending'`) брони и
   проводит их по трём ступеням в зависимости от того, сколько осталось
   до мероприятия:
   - **≤ `REMINDER_HOURS_BEFORE`** (по умолчанию 12ч) — первое
     напоминание с двумя кнопками-**ссылками** «✅ Подтверждаю» /
     «❌ Не смогу прийти» (`/rsvp/<бронь>/confirm` и `.../decline`).
   - **≤ `REMINDER_SECOND_HOURS_BEFORE`** (6ч) — то же самое ещё раз,
     если гость так и не ответил на первое.
   - **≤ `REMINDER_CANCEL_HOURS_BEFORE`** (3ч) — если ответа всё ещё
     нет, бронь снимается автоматически (`status = 'cancelled'`,
     `attendance_status = 'expired'`), место освобождается на сайте, а
     гостю и в `TELEGRAM_STAFF_CHAT_ID` (если задан) уходит уведомление.
4. Открытие ссылки «Подтверждаю»/«Не смогу прийти» — само по себе
   действие (не нужен отдельный клик на сайте): сразу меняет
   `attendance_status`, а при отмене ещё и освобождает место. Если гость
   нажмёт на уже неактуальную ссылку (бронь успела сгореть по 3-й
   ступени) — сайт честно покажет «Бронь больше не активна», а не
   «Подтверждено».

Никакого отдельного бота с обработкой нажатий не нужно — кнопки-ссылки
просто открывают URL, вся логика подтверждения живёт на уже
существующем сервере (два новых роута: `telegramWebhook.js` и `rsvp.js`).

### Настройка

В `.env` (или в переменных окружения Render — уже прописаны в
`render.yaml`, кроме секретных):

```
TELEGRAM_BOT_TOKEN=...       # от @BotFather, секрет
TELEGRAM_BOT_USERNAME=...    # без @
TELEGRAM_STAFF_CHAT_ID=      # необязательно — куда слать уведомления об отменах
REMINDER_HOURS_BEFORE=12         # первое напоминание
REMINDER_SECOND_HOURS_BEFORE=6   # повтор
REMINDER_CANCEL_HOURS_BEFORE=3   # автоотмена, если всё ещё нет ответа
PUBLIC_BASE_URL=...          # на Render не нужен — берётся из RENDER_EXTERNAL_URL сам
```

При старте сервер сам регистрирует вебхук в Telegram (`setWebhook`), если
`TELEGRAM_BOT_TOKEN` и публичный адрес заданы — вручную ничего вызывать
не нужно, просто передеплой на Render с настроенными переменными.

Планировщик напоминаний — это обычный `setInterval` внутри процесса, а
не отдельный Cron Job. На платном тарифе Render (см. раздел про
хостинг ниже) сервис не "спит", так что напоминания уходят вовремя. На
бесплатном тарифе сервис засыпает от бездействия, и напоминания уйдут с
опозданием — при переходе обратно на free tier стоит завести отдельный
Render Cron Job, который раз в N минут дёргает публичный эндпоинт.

## Опрос по итогам визита

Для каждой брони со статусом `paid` (оплаченное мероприятие или
подтверждённая через Telegram бесплатная бронь), для которой прошло
`SURVEY_HOURS_AFTER_EVENT` часов с начала мероприятия, сервер:

1. Создаёт запись `surveys` с уникальным токеном и шлёт гостю ссылку
   `/survey/<токен>` на мобильную форму (4 категории — обслуживание,
   еда, напитки, общее впечатление — по шкале 1-5, плюс необязательное
   поле «Пожелания/отзыв»):
   - в Telegram, если у брони есть `telegram_chat_id` (гость подтверждал
     бронь через бота);
   - иначе на email гостя (через `EmailService`, как билет).
2. При отправке формы ответы сохраняются, а в чат персонала
   (`TELEGRAM_STAFF_CHAT_ID`) сразу уходит сообщение `#Опрос` с
   оценками; если гость написал текст — вторым сообщением `#отзыв` с
   этим текстом. Повторно один и тот же токен отправить нельзя (форма
   один раз показывает «Спасибо», без дублей в чате).
3. По понедельникам с 09:00 до 12:00 (по Анталии) сервер раз в неделю
   считает средние баллы по всем ответам за последние 7 дней и шлёт
   сводку `#Опрос` тем же чатом персонала.

Настройка (в `.env` / переменных Render):

```
SURVEY_HOURS_AFTER_EVENT=18   # через сколько часов после НАЧАЛА мероприятия слать ссылку
```

Без `TELEGRAM_STAFF_CHAT_ID` пересылка ответов и еженедельная сводка
просто не отправляются (гость всё равно может пройти опрос, ответы
остаются в БД). Точного времени окончания мероприятия в системе нет,
поэтому таймер считается от времени начала — при `=18` для вечернего
мероприятия ссылка обычно уходит в течение следующего дня.

## Хостинг

Код лежит на GitHub: https://github.com/zakinternational07-bot/my-friends-pub-antalya
(приватный репозиторий).

### Render — текущий хостинг (платный тариф + постоянный диск)

В репозитории есть `render.yaml` — Render подхватит его сам и настроит
почти всё автоматически:

1. Зарегистрироваться на https://render.com (можно через GitHub-аккаунт).
2. New → Blueprint → выбрать репозиторий `my-friends-pub-antalya`.
3. Render найдёт `render.yaml` и предложит создать сервис `my-friends-pub-antalya`
   на тарифе **Starter** (платный, ~$7/мес) с постоянным диском 1 ГБ.
   Единственное, что попросит ввести вручную — `ADMIN_PASSWORD` (пароль
   от админки). Остальные переменные окружения уже прописаны в blueprint
   (`SESSION_SECRET` сгенерируется сам, `PAYMENT_PROVIDER=mock`,
   `EMAIL_PROVIDER=console` и т.д. — тестовый режим оплаты/писем).
4. Если сервис уже существует и Blueprint просто обновляется (например,
   план/диск добавлены позже) — Render может попросить подтвердить это
   вручную: **Settings → Disks → Add Disk**, mount path `/var/data`,
   размер 1 ГБ (значение стоит и в `render.yaml`, но платные ресурсы
   Render иногда просит подтверждать через UI, а не только через
   Blueprint sync).
5. Deploy — через несколько минут сайт будет доступен по адресу вида
   `https://my-friends-pub-antalya.onrender.com`.

**Почему платный тариф с диском, а не бесплатный:** на бесплатном тарифе
диск эфемерный — файл `mfp.sqlite` (брони, опросы гостей и т.д.)
пересоздаётся с нуля при каждом деплое и после долгого простоя, сервис
"засыпает" после ~15 минут без запросов. Это было терпимо, пока сайт был
демо, но с реальными бронями и отзывами гостей терять данные при каждом
деплое неприемлемо. Тариф **Starter** не спит, а диск, смонтированный по
пути `/var/data` (переменная `DATA_DIR` в `render.yaml` указывает
серверу писать `mfp.sqlite` именно туда), переживает деплои и рестарты.

Постоянный диск покрывает и sqlite, и файлы, загруженные через админку
в мероприятия: `backend/src/middleware/upload.js` сохраняет их в
`DATA_DIR/uploads/images/events/` и `.../video/events/` (переживает
деплои так же, как база), а не в `frontend/assets/` — та папка
пересоздаётся из git при каждом деплое. Отдаются такие файлы отдельным
static-роутом `/uploads/...` (см. `server.js`), а не `/assets/...`.
Медиа мероприятий этой недели, закоммиченные прямо в репозиторий (см.
`backend/src/db/seed.js`), по-прежнему живут в `frontend/assets/` — им
персистентность не нужна, они и так часть кода.

### Продакшен (когда сайт станет боевым, не демо)

- **Простой**: один VPS (например, обычный хостинг с Node.js) — Express
  раздаёт и API, и статику фронтенда, как сейчас локально.
- **Раздельный**: фронтенд на Vercel/Netlify (статика из `frontend/`),
  backend на Railway/Render на платном тарифе с постоянным диском
  (нужен постоянно работающий процесс из-за WebSocket и SQLite-файла —
  либо перейти на управляемую БД, например Postgres через Supabase —
  схема в `backend/src/db/schema.sql` переносится почти без изменений).

В обоих случаях: включить HTTPS, сгенерировать длинный случайный
`SESSION_SECRET`, сменить `ADMIN_PASSWORD` на надёжный, подключить
реальный платёжный шлюз и почтовый сервис (см. выше).

## Структура проекта

```

```

в комментариях внутри `backend/src/db/schema.sql` и
`backend/src/services/seatHold.js`.
